    3.1 Expert MLPs as named FFNs¶

    Section 2.6 closed the dense baseline as the first row of the comparison table. The MoE rows that the next eight chapters will add to that table differ from the dense row in exactly one place: the FFN sub-layer. This section makes the smallest possible move toward that difference — it clones the dense FFN four times and labels the copies expert 0 through expert 3. No router yet, no selection logic, no dispatch. The point of starting here is to show that an "expert" is not a new kind of object; it is the FFN from Section 2.4, instantiated \(E\) times under a list-indexed name.

    Figure 3.1 — On the left, Chapter 2's single DenseFFN. On the right, four ExpertMLP instances stacked in an ExpertBank, each with its own \(W_1^{(i)}\) and \(W_2^{(i)}\) but the same shape contract as the dense block. Today every expert sees every token (the faint arrows from \(x\) fan out to all four); Section 3.2 will replace those fans with a sparse selection. Rendered via TikZ in the PDF version.

   today: forward_all(x) runs every expert (E·2DH params total).
   Chapter 3.2: a router will choose K << E of them per token, so active params/token stay ~K·2DH.

    Take the chapter-3 anchor mini-example: keep the chapter-2 shape constants \(B = 2\), \(T = 8\), \(D = 16\), \(H = 64\) and add \(E = 4\) experts. The bank stores \(E \cdot 2 D H = 4 \cdot 2{,}048 = 8{,}192\) parameters, the four-times-larger version of the \(2{,}048\)-parameter dense FFN. The total column of the comparison table moves; the active per token column will catch up only when a router lands.

    Name the new objects. We keep \(B, T, D, H\) from earlier chapters. The constants \(E\) (the number of routed experts, declared in Section 1.2) and \(K\) (the top-\(K\) choice, declared in the same section) finally enter live code; for this section we use \(E = 4\) and have not yet introduced selection, so \(K\) does not appear until Section 3.3. One new code object: ExpertBank, an nn.ModuleList of \(E\) ExpertMLP instances exposed through bank[i] for any expert index \(i \in \{0, \dots, E-1\}\) and through forward_all(x) as a diagnostic helper that runs every expert on the same input.

    Table 3.1 — Dense FFN versus the chapter-3 expert bank. The bank stores \(E\) copies of the same shape; the router (Section 3.2) will choose which subset of them actually runs per token.

    A single expert is identical, line for line, to the dense FFN of Section 2.4.

    \[ \mathrm{ExpertMLP}_i(x) \;=\; \mathrm{GELU}\bigl(x\, W_1^{(i)}\bigr)\, W_2^{(i)}, \qquad W_1^{(i)} \in \mathbb{R}^{D \times H}, \;\; W_2^{(i)} \in \mathbb{R}^{H \times D}, \qquad i \in \{0, 1, \dots, E-1\}. \]

    The equation is the dense-FFN equation from Section 1.1 with a per-expert superscript on the weights. Nothing else changes. In particular, the constructor signature ExpertMLP(d_model, hidden) is the one locked in Section 1.6: ch03.ExpertMLP is a subclass of the Chapter 1 skeleton, so isinstance(expert, ch01.ExpertMLP) holds and check_signatures() from Section 1.6 still passes after Chapter 3 lands. The "expert" framing is purely organisational — which expert this MLP represents is the position of its module in the bank's list, not a field stored inside the module.

    from moe_from_scratch.ch01 import ExpertMLP as _ExpertMLPSkeleton  # locked signature

class ExpertMLP(_ExpertMLPSkeleton):
    def __init__(self, d_model, hidden):
        super().__init__(d_model=d_model, hidden=hidden)
        self.up   = nn.Linear(d_model, hidden,  bias=False)        # W1: (D, H)
        self.down = nn.Linear(hidden,  d_model, bias=False)        # W2: (H, D)
    def forward(self, x):                                          # (*, D) -> (*, D)
        return self.down(F.gelu(self.up(x)))

class ExpertBank(nn.Module):
    def __init__(self, n_experts, d_model, hidden):
        super().__init__()
        self.n_experts, self.d_model, self.hidden = n_experts, d_model, hidden
        self.experts = nn.ModuleList([
            ExpertMLP(d_model=d_model, hidden=hidden) for _ in range(n_experts)
        ])
    def forward_all(self, x):                                      # (*, D) -> (E, *, D)
        return torch.stack([expert(x) for expert in self.experts], dim=0)

# Mini-example (chapter anchor E=4, D=16, H=64, B=2, T=8):
bank  = ExpertBank(n_experts=4, d_model=16, hidden=64)
slabs = bank.forward_all(torch.randn(2, 8, 16))                    # (4, 2, 8, 16)
assert slabs.shape == (4, 2, 8, 16)
assert sum(p.numel() for p in bank.parameters()) == 4 * 2 * 16 * 64 == 8192

    The diagnostic for this section is the strongest possible no-collusion check: run every expert on the same input and verify that (a) each output preserves the \((B, T, D)\) shape, and (b) no two experts produce the same output. Property (b) is what makes the bank useful — if random initialisation collapsed every expert onto the same function, dispatch would be meaningless. With \(E = 4\) and seed \(0\) all \(\binom{4}{2} = 6\) pairs produce distinct outputs on a fresh \((B, T, D)\) batch.
